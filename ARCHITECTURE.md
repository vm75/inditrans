# Architecture

## Purpose and scope

This document describes the internals of the `inditrans` transliteration engine
(`native/src/`), the FFI/WASM boundary, and the Dart wrapper. It is aimed at
contributors who need to understand how a transliteration call travels from Dart through
C++ and back. It intentionally omits platform plugin scaffolding and example apps.

---

## System context

```
Dart caller
    │  transliterate(text, from, to, options, skipStart, skipEnd)
    ▼
flutter/lib/inditrans.dart      ← public Dart API (universal_ffi)
    │  FFI call (native) / JS interop (Web)
    ▼
native/src/inditrans.cpp        ← single-source C++23 engine
    │  compiled to
    ├─ libinditrans.so / inditrans.dll  (Android, iOS, Linux, macOS, Windows)
    └─ flutter/assets/inditrans.wasm   (Web via Emscripten)
```

The C++ engine has **no runtime I/O**. Script metadata is compiled into typed constexpr records in `native/src/script_metadata.h`. The six fixed transliteration tables are fixed-size `std::array<ScriptStringRef, N>` fields in each record; aliases, equivalents, and languages use compact ranged tables. All metadata types are hand-written in `type_defs.h`. A deduplicated length-prefixed UTF-8 pool stores string bytes once.

## Components

| Component | File(s) | Responsibility |
|---|---|---|
| **C export layer** | `native/src/exports.h`, `inditrans.cpp` (bottom) | Stable C ABI: `transliterate`, `isScriptSupported`, `releaseBuffer` |
| **ScriptMetadata** | `native/src/inditrans.cpp`, `script_metadata.h` | Resolves canonical names and aliases against constexpr records and their flattened ranges |
| **ScriptReaderMap** | `native/src/inditrans.cpp` | Builds a `Char32Trie<ScriptToken>` for tokenising one script (or all Indic scripts via the `indic` virtual script) |
| **ScriptWriterMap** | `native/src/inditrans.cpp` | Holds indexed `string_view` arrays for writing into one target script |
| **InputReader** | `native/src/inditrans.cpp` | Walks UTF-8 input, emits a `vector<TokenOrString>`, then yields `TokenUnit` objects one at a time with script-specific grouping |
| **OutputWriter** | `native/src/inditrans.cpp` | Consumes `TokenUnit` objects and appends target graphemes to a `Utf8StringBuilder` |
| **Trie infrastructure** | `trie.h`, `char_trie.h`, `utilities.h` | Two trie variants: `Char32Trie<V>` (runtime, heap) and `CharTrie` (compile-time flat array) |
| **UTF-8 utilities** | `native/src/utf.h` | Zero-dependency, constexpr UTF-8↔UTF-32 encode/decode; `Utf8StringBuilder` output buffer |
| **Script metadata** | `native/src/script_metadata.h` | Generated data-only UTF-8 pool, typed per-script fixed character arrays, and ranged alias/equivalent/language tables |
| **Script data source** | `tool/script_data.json`, `native/src/script_data.h` | JSON is the source; the legacy NUL-delimited header is still generated alongside the constexpr metadata |
| **Constants** | `native/src/script_constants.h`, `type_defs.h` | `TokenType`, `ScriptType`, `Token`, `ScriptToken`; Vedic accent lists; Tamil prefix list |
| **Dart API** | `flutter/lib/inditrans.dart` | Calls C functions via `universal_ffi`; enforces read/write restrictions per script |
| **FFI bindings** | `flutter/lib/src/bindings.dart` | Auto-generated by `ffigen` from `exports.h`; do not edit |

## Dependency direction

```
exports.h
    ↑
inditrans.cpp ← script_metadata.h
              ← script_constants.h
              ← type_defs.h
              ← utilities.h (→ trie.h, utf.h)
              ← char_trie.h (→ type_defs.h)
              ← utf.h
```

`inditrans.cpp` is the only translation unit. All other `.h` files are either
inlined utilities or constant data. Nothing in `native/src/` depends on Flutter,
Dart, or platform APIs.

## Data model

### Script metadata (`script_metadata.h`)

`tool/script_data.json` is the source for the generated script metadata.
`tool/generate_headers.dart` emits data only: one deduplicated, length-prefixed UTF-8 byte pool, per-script fixed character arrays, and compact variable metadata tables. The C++ types and invariants live in `type_defs.h`. A `string_view` is materialized only when a `ScriptStringRef` is accessed; names and aliases are resolved without runtime parsing or metadata containers.

Each metadata record contains:
- **type** — `Indic`, `Tamil`, `Latin`, or `Others`
- **isVedic** — whether the script carries Vedic accent marks
- **vowels**, **vowelMarks**, **consonants**, **otherDiacritics**, **symbols**, **vedicSymbols** — parallel indexed arrays
- **aliases** — alternative names accepted as input
- **equivalents** — additional input spellings that map to a canonical token

### Token model

```
TokenType   = Vowel | VowelMark | Consonant | OtherDiacritic | Accent |
              Symbol | VedicSymbol | ExclusiveSymbol | Ignore
ScriptType  = Indic | Tamil | Latin | Others

Token       = { TokenType, idx }         ← position within a category array
ScriptToken = { TokenType, idx, ScriptType, extra? }
TokenUnit   = { leadToken: ScriptToken, vowelMark: Token,
                otherDiacritic: Token, accent: Token }
```

`idx` is the **0-based position** within the shared consonant/vowel ordering
(Devanagari-derived). The same index across all Indic scripts always refers to
the same phoneme, making cross-script lookup a simple array index operation.

`TokenUnit` groups a consonant or vowel with its attached diacritics. A
`TokenOrString` is a `std::variant<ScriptToken, std::string_view>` — the
`string_view` branch carries untransliterated runs (XML tags, skip regions,
unrecognized characters).

## Transliteration pipeline

Every call to `transliterate(input, from, to, options, skipStart, skipEnd)` runs
five stages:

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. LOOKUP CACHED MAPS                                           │
│    getScriptReaderMap(from)  →  ScriptReaderMap (Char32Trie)    │
│    getScriptWriterMap(to)    →  ScriptWriterMap (index arrays)  │
│    (built once, cached in static unordered_map)                 │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 2. SCAN (InputReader constructor)                               │
│    Walk UTF-8 input byte-by-byte using Char32Trie longest-match │
│    Emit vector<TokenOrString>:                                  │
│      • ScriptToken  — recognized grapheme                       │
│      • string_view  — XML tag / skip region / unrecognized run  │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 3. GROUP (InputReader::getNext)                                 │
│    Pull tokens from the vector and group into TokenUnit:        │
│      Indic:  consonant + optional VowelMark/OtherDiacritic/Acc  │
│      Tamil:  as Indic, plus superscript/subscript consonant     │
│              variants and Tamil allophone rules (word position, │
│              hard/soft/medial consonant context, prefix detect) │
│      Latin:  consonant + following vowel or explicit virama     │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 4. WRITE (OutputWriter::writeTokenUnit)                         │
│    Look up each TokenUnit field in ScriptWriterMap index arrays │
│    Apply output-side rules:                                     │
│      Indic:  straightforward index lookup + optional virama     │
│      Tamil:  ந→ன positional swap, TamilTraditional substitution,│
│              superscript handling, anuswara inference           │
│      Latin:  consonant + inferred inherent vowel or virama      │
│    Append to Utf8StringBuilder (doubling growth policy)         │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 5. RETURN                                                       │
│    release() the StringBuilder's heap buffer → caller owns it  │
│    Dart side calls releaseBuffer() via FFI after copying        │
└─────────────────────────────────────────────────────────────────┘
```

### Map caching

`ScriptReaderMap` and `ScriptWriterMap` objects are constructed once per script
name and cached in file-static `unordered_map`s. Subsequent calls for the same
`(from, to)` pair pay only a hash-map lookup.

### The `indic` virtual script

When `from = "indic"`, `getScriptReaderMap` constructs a single `ScriptReaderMap`
seeded with Devanagari and then calls `addScript` for every other Indic/Tamil
script. The resulting trie can decode input from any Brahmic script in one pass
without knowing the source script in advance.

## Invariants

- Consonant index 0–36 maps to the shared Devanagari-derived ordering in every
  script. Any change to this ordering breaks cross-script symmetry.
- Latin scripts do not store `VowelMark` entries in `ScriptReaderMap`
  (only the virama position is used). The inherent vowel is always inferred
  at the writer side.
- `readableLatin` and `wx` are write-only: `ScriptReaderMap` returns `nullptr`
  for them. This is enforced both in C++ (`isWriteOnlyScript`) and in Dart.
- `indic` is a read-only virtual script: `ScriptWriterMap` returns `nullptr`
  for it. Dart enforces this restriction before the FFI call.
- The output buffer is owned by the C++ engine until `releaseBuffer()` is called.
  The Dart layer copies the result string and then calls `releaseBuffer` via the
  binding, completing the handoff. Never pass the raw pointer across async
  boundaries.
- Vedic accents are silently dropped when the target script is a non-Vedic Indic
  script (`IgnoreVedicAccents` is OR-ed in automatically by `getOutputWriter`).

### Native ABI and Windows cross-compilation

- **Plain C ABI**: The exported boundary (`native/src/exports.h`) exposes only `extern "C"`
  functions (`transliterate`, `isScriptSupported`, `releaseBuffer`). No C++ classes,
  STL types (`std::string`, `std::vector`), templates, or exceptions cross the DLL boundary.
- **Windows cross-compilation**: The Windows x86-64 DLL (`inditrans.dll`) is cross-compiled
  from Linux using MinGW-w64 (`x86_64-w64-mingw32-g++`) and configured via
  `tool/cmake/mingw64.cmake`.
- **Compiler standard**: The internal implementation requires C++23
  (`set(CMAKE_CXX_STANDARD 23)`). MinGW GCC ≥ 13 is enforced by CMake.
- **ABI independence**: Because the public interface is pure C, MinGW C++ ABI differences
  from MSVC (e.g. name mangling, libstdc++ vs MSVC STL) do not affect external callers.
  Applications and language bindings compiled with MSVC, Clang, or Dart FFI can load and use
  `inditrans.dll` without compatibility issues.
- **Self-contained runtime**: The Windows DLL target specifies `-static-libgcc -static-libstdc++`
  to eliminate runtime dependencies on `libstdc++-6.dll` and `libgcc_s_seh-1.dll`.

## Script-specific rules (implemented in InputReader / OutputWriter)

| Feature | Location |
|---|---|
| Tamil allophone selection (hard/soft/medial context) | `InputReader::readTamilTokenUnit` |
| Tamil ந→ன word-medial swap | `OutputWriter::writeTamilTokenUnit` |
| Tamil superscript/subscript consonant variants | `InputReader::readTamilTokenUnit` |
| Tamil prefix detection (`TamilPrefixLookup`) | Both reader and writer, `StatefulTrie<TokenUnit,bool>` |
| Gurmukhi adhak (gemination marker) | `InputReader::inferGurmukhiAdhak` |
| Anuswara nasal assimilation | `OutputWriter::inferAnuswara` |
| XML/HTML tag pass-through | `InputReader` constructor |
| `##`-delimited skip regions | `InputReader` constructor |
| Vedic accent stripping | `InputReader` (read side, `IgnoreVedicAccents`) and `OutputWriter` (write side) |

## Trie infrastructure

Two trie implementations coexist for different use cases:

| Class | Key type | Value type | Allocation | Purpose |
|---|---|---|---|---|
| `Char32Trie<V>` | `char32_t` | any | heap, `unordered_map` nodes | Runtime tokeniser trie per script |
| `CharTrie` | `uint16_t` | `ScriptToken` | compile-time flat `uint8_t[]` | Optional compile-time-baked trie (currently unused path) |
| `StatefulTrie<K,V>` | any | any | heap | Tamil prefix detection with incremental lookup state |
| `StringMap<C,V>` | string | any | heap, `unordered_map` | Longest-match string lookup (general utility) |

`Char32Trie` performs longest-match: it descends until no child exists and
returns the deepest value found so far. This handles multi-codepoint grapheme
sequences (e.g., a consonant followed by a combining mark).

## Extension points

- **New script**: add a record to `tool/script_data.json`; regenerate headers
  and package script lists with `dart tool/generate_headers.dart`. Update
  `flutter/lib/src/script.dart` and `nodejs/src/Script.ts` when their public
  script restrictions need to change.
- **New option flag**: add a value to `TranslitOptions` in `native/src/exports.h`;
  mirror it in `flutter/lib/src/option.dart` and `nodejs/src/Option.ts`; handle it in
  `InputReader` or `OutputWriter`; regenerate bindings.
- **Script alias**: add the alias to the script record in `tool/script_data.json`
  and regenerate headers; no engine code change is required.
- **Script equivalents** (alternate input spellings): add them to the script's
  `equivalents` map in `tool/script_data.json` and regenerate headers.
